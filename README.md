# Local RAG Assistant with Microsoft Foundry Local

> Final project — **Microsoft Summer School 5 (2026)**, Foundry Local track.
> Supervisor: Barbaros Günay. Presentation: [`presentation.pptx`](presentation.pptx)

An offline question-answering assistant that answers questions about your own
course notes. It runs **entirely on your machine** — no internet, no cloud
account — using Microsoft Foundry Local for on-device model inference and the
**RAG (Retrieval-Augmented Generation)** pattern to ground answers in your
documents.

## What it does

You drop your notes (`.txt`, `.md`, `.pdf`, `.docx`) into a folder, run one
indexing script, and then ask questions in plain English. The assistant finds
the most relevant passages from your notes and has a local Large Language Model
(LLM) write an answer using only those passages — citing the source file, and
refusing to answer when the notes don't cover the question.

## How it works (the RAG pipeline)

```
Your notes  ->  chunk  ->  embed  ->  SQLite (rag.db)
                                          |
Question  ->  embed  ->  similarity search + relevance gate
                                          |
                        top chunks  ->  prompt  ->  local LLM  ->  grounded answer
```

| Component | Role | This project |
|-----------|------|--------------|
| Data source | Documents to answer from | Files in `docs/` |
| Embeddings | Turn text into meaning-vectors | `qwen3-embedding-0.6b` (1024-dim) |
| Vector store | Hold text + vectors | SQLite file `rag.db` |
| Retriever | Find relevant chunks for a question | Cosine similarity + relevance gate |
| Generator | Write the final answer | `phi-3.5-mini` via Foundry Local |

## Requirements

- Windows (this build uses the `-winml` SDK; macOS/Linux would use `foundry-local-sdk`)
- Python 3.11 or later
- Microsoft Foundry Local (installed via `winget install Microsoft.FoundryLocal`)
- ~8 GB RAM

## Setup

```bat
:: 1. Install the Foundry Local runtime (one time, needs admin)
winget install Microsoft.FoundryLocal

:: 2. In the project folder, create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate

:: 3. Install Python dependencies
pip install -r requirements.txt
```

## Usage

```bat
:: 1. Put your notes into a docs\ folder (txt, md, pdf, or docx)

:: 2. Build the index (embeds every chunk into rag.db). Re-run when notes change.
python ingest.py

:: 3. Ask questions
python app.py
```

Type a question at the prompt; type `quit` to exit. Example:

```
Question: how much is the deposit for a laptop?
  [retrieved from: laptop-policy.md, membership-faq.md | top score 0.625]

Answer: The deposit for a laptop is 500 TL.
  Sources: laptop-policy.md

Question: what is the wifi password?

Answer: I don't have that in your notes.
  (best match scored 0.343, below the 0.40 threshold)
```

The `Sources:` line is produced by the program, not written by the model — see
"Citations are resolved in code" below.

## Key design decisions

- **Chunking (~800 chars, sentence-aware).** Documents are split into passages so
  retrieval returns a focused answer, not a whole file. The splitter breaks
  oversized blocks by sentence, which took one test PDF from 3 useless mega-chunks
  to 41 usable ones — the single biggest lever on answer quality.
- **Embed once, store, reuse.** Indexing (`ingest.py`) is separate from querying
  (`app.py`), so embeddings are computed one time, not on every question.
- **Two independent refusal mechanisms, because they fail in different places.**
  Before calling the model, the app checks the top chunk's similarity score; below
  0.40 the question is refused without running the model, at 0.1 s instead of ~5 s.
  The model is *also* instructed to refuse when the context doesn't answer the
  question. Testing showed each catches cases the other misses — two off-topic
  questions scored above the gate and were caught only by the model. The gate is
  fast and model-independent but blunt; the model actually reads the passage but
  is slower and less predictable. Keeping both is the point.
- **The threshold is calibrated, not chosen.** 0.40 suits this corpus. It is
  **not** a constant of the system: the same question scored 0.490 against one
  document set and 0.301 against another. Re-calibrate when the documents change
  — see [`EVALUATION.md`](EVALUATION.md).
- **`TOP_K = 5`, not 3.** At 3, retrieval filled up with chunks from a single
  file and a question needing two documents never saw the second one.
- **Citations are resolved in code, not written by the model.** The context is
  numbered (`[1] from laptop-policy.md`); the model marks passages as `[1]`, and
  `resolve_citations()` maps those numbers to filenames. When the model was asked
  to write filenames itself, citation accuracy collapsed from 10/11 to **4/11**
  as soon as `TOP_K` rose to 5 — more context crowded out the instruction.
  Moving the bookkeeping into the program restored it to **11/11**.
- **Model choice: `phi-3.5-mini`.** A tiny 0.5B model answered general-knowledge
  questions it should have refused ("capital of France"). The 3.8B `phi-3.5-mini`
  follows the "use only the context" instruction far better, at a cost of a few
  seconds per answer. For a notes assistant, grounding beats raw speed.

## Evaluation summary

**Single document** (`evaluate.py` → [`eval_results.md`](eval_results.md)) —
10 questions over one 13-page PDF. **7 pass, 2 partial, 1 fail**, averaging 5.4 s.
Every verdict was checked against the source text.

- Answerable questions were answered correctly; three cited the source cleanly.
- Two answers were right but cited `learn.microsoft.com` — a reference tag copied
  out of the PDF's own text rather than the filename.
- One answer described Weeks 1–2 when asked about Week 1 (lowest retrieval score
  of the set, 0.422).
- "Tell me a joke" scored **0.490 — higher than four genuine questions** — cleared
  the gate, and the model then invented an anecdote that is not in the document.
  A hallucination with a citation attached: the exact failure RAG should prevent.

**Multiple documents** (`evaluate_multi.py`, corpus in [`tests/`](tests/README.md)) —
16 questions over four deliberately overlapping documents, grading retrieval,
top-1 ranking, answer content and *citation accuracy* as four separate measures.
With a one-document corpus, citing the right source is unavoidable and therefore
untested; this corpus makes it possible to get the fact right and the source wrong.

**Final: 14 pass, 2 partial, 0 fail.**

| Measure | Result |
|---|---|
| Correct file retrieved (top-5) | 11/11 |
| Correct file ranked #1 | 11/11 |
| Correct fact in the answer | 11/11 |
| Correct file cited | 11/11 |
| Answers citing an *extra* file | 2/11 |
| Non-answerable questions handled | 5/5 |
| Average answered question / gated refusal | 5.8 s / 0.1 s |

Getting there took six runs, each testing one hypothesis — including two results
that contradicted what this README previously claimed.
**[`EVALUATION.md`](EVALUATION.md) is the full write-up**, and every run's raw
output is committed alongside it.

## Limitations

- **The gate threshold is corpus-specific.** 0.40 works here. It is not
  transferable: the same off-topic question scored 0.490 against one document set
  and 0.301 against another. Anyone reusing this code on their own notes must
  re-calibrate, and nothing in the code currently forces them to.
- **Over-citation.** Two answers in eleven cite one file more than they used. The
  correct source is always among them — the defect is extra files, never a wrong
  file instead of the right one. Tightening the prompt moved the problem between
  questions rather than removing it, so it appears to be model variance.
- **Small local model.** `phi-3.5-mini` is capable but can still be verbose, and
  it follows secondary instructions unevenly as context grows.
- **Scanned/image-only PDFs** yield no text without OCR (not included).
- **Brute-force search.** All vectors are scored in Python, which is fine for a
  few hundred chunks but would need a real vector index (e.g. FAISS / sqlite-vec)
  at large scale.
- **Single-run measurements.** One run per configuration, 16 questions, four
  synthetic documents. Enough to expose the effects described; not enough for
  statistical claims.

## Possible improvements

- **Ship a calibration script** that sweeps thresholds against a handful of
  known-good and known-bad questions and reports the separating value. This is
  the most useful missing piece — the threshold is currently a hardcoded number
  that is only correct for one corpus.
- Format embedding queries with the model's instruction prefix, which may widen
  the gap between relevant and irrelevant chunks.
- Add OCR for scanned PDFs.
- Swap brute-force search for a vector index to scale to large document sets.
- Add a simple UI (Streamlit or Gradio) over `answer_query()`.

## Demo script (for the presentation)

1. **Problem:** "General chatbots don't know *my* notes, and they make things up."
2. **Show the documents** in `docs/` and run `python ingest.py` (explain chunking).
3. **Ask an answerable question** — show the grounded answer and its `Sources:` line.
4. **Ask an unanswerable question** — show it refused at the gate in 0.1 s.
5. **Lesson learned:** the biggest wins came from the data and the plumbing, not
   the model — and two things I believed after the first evaluation turned out to
   be wrong once I tested them properly.
